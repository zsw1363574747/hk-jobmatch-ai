# 薪酬参考（报表）设计 · 替代原来的 C/D 推断

> 原来的「基准库 + 模型推断」不做了：误差大、解释成本高，你不放心，我也没法保证。
> 现在改成两块，都只用平台自己的数据：
> 1. **单条岗位**：JD 明码 → 探针（B-）→ 探不到就写「未披露」，不猜。
> 2. **关键词参考**：一张报表，给「这个关键词大概什么价、相邻岗位什么价」，供判断用。

---

## 1. 单条岗位：只剩两级

```
JD 写了        → 28–35K（A）
JD 没写        → 探针反推 ≈25–40K（B-）
探针也探不到   → 未披露
```

没有模型、没有推断值。探针就是上一版已经上线的那个：
`salarytype=monthly` + `salaryrange=档位` + 公司名，看岗位落在哪些档，扣回 5k。

---

## 2. 关键词参考：用「档位计数」代替逐条猜

平台对每个薪资档都会返回一个 `totalCount`。把 11 个档问一遍，就得到这个关键词的**薪资分布**：

```
"product manager"（每档一次请求，共 11 次）
10-15k: 92   15-20k: 274   20-25k: 898   25-30k: 1262  30-35k: 1697
35-40k: 1400 40-45k: 1569  45-50k: 1219  50-55k: 823   55-60k: 1034  60k+: 705
→ 中位数 37.5K，P25–P75 32.5–47.5K
```

**为什么这样准**：这些计数包含「雇主填了但没展示」的岗位，也就是探针用的同一份数据，只是聚合了。
**成本**：11 次请求/关键词，≈4 秒。主关键词 + 5 个相关岗位 ≈ 37 秒。

校准（实测）：

| 关键词 | 档位法中位数 | 明码样本中位数 |
|---|---|---|
| data analyst | 32.5K | 31.5K |
| accountant | 32.5K | 35.0K |

误差 1–2K，做参考够用；**不拿它冒充某条岗位的薪资**。

### 2.5 探针（单条反查）的实测精度

2026-11-09 用 **58 条雇主公开了月薪的岗位**当答案，对线上探针做盲测：

| 指标 | 结果 |
|---|---|
| 中点误差中位数 | 2.0%（约 500 港元） |
| ±10% / ±20% 内 | 93% / 96% |
| 真值中点落在反推区间 | 78% |
| 区间与真值有交集 | 95% |

结论：**中点可信，区间偏窄**；2/58 的岗位平台隐藏薪资与公开薪资矛盾，会产生大幅误差。
方法和明细见 [salary-calibration.md](salary-calibration.md)。

## 3. 相关岗位从哪来

`bundle/data/role-graph.json`：关键词 → 3–7 个相邻岗位，中英文各一份。

```json
"product manager": ["project manager","business analyst","operations","ux designer","frontend developer","backend developer","data analyst"]
```

没配置的关键词就只出它自己那一行，并在界面提示「可以在这个文件里加」。
这张表是**配置**不是算法——你觉得某个词的相关岗位不对，直接改文件，不用动代码。

## 4. 报表长什么样

```
岗位 / 关键词        岗位数    中位数    P25–P75
★ product manager    2842    37.5K    32.5K–47.5K
  project manager   10823    37.5K    27.5K–47.5K
  business analyst   7337    37.5K    27.5K–47.5K
  operations        15669    32.5K    22.5K–42.5K
  ux designer         446    32.5K    22.5K–42.5K
  frontend developer  848    37.5K    27.5K–42.5K
```

- 「岗位数」是关键词的搜索结果总数（不加薪资筛选），用来看样本厚不厚。
- 中位数不是平均数：不会被几个 80K+ 拉飞。
- 界面在左栏「薪酬参考」，点一次生成，不自动跑（37 秒，别拖慢搜索）。

## 5. 已知偏差（用的时候心里有数）

1. **匹配是宽的**：JobsDB 的 `keywords` 会在标题和正文里做宽匹配。
   `product manager` 会带进一些只含 manager 的岗位，所以表里相邻岗位之间差距不大。
   我试过加引号做精确匹配，结果只剩 5–200 条，样本太少，反而更不准 —— 所以没加。
2. **档位会外扩**：平台筛选命中区间向外多一档（±5k），分布被轻微抹平，**中位数稳，尾部分位不要用**。
3. **只反映挂了薪资的岗位**：完全不填薪资的公司不在统计里，可能整体偏低或偏高。
4. **口径**是 base 月薪；13 薪 / 花红不在里面。

## 6. 徽章（登录后）

单条岗位的「薪酬相符」徽章还是在详情里读（`session.js`），登录了才生效。
报表层面不做徽章统计——那需要逐条渲染上万个岗位，不划算。
